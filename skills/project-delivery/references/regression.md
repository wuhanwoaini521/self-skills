# Regression

回归面**按改动风险选**，不是固定全量跑。按下表选择：

| 改动类型 | 回归范围 |
| --- | --- |
| bug fix | 受影响的流程 + 相邻行为（同一模块的其它入口、共享 helper 的其它调用方） |
| 共享组件 / 公共工具 | 所有主要消费者；至少覆盖主要调用路径 |
| API / 契约变更 | 所有调用方兼容性；旧调用方式是否仍可用 |
| 数据库 / 迁移 | 迁移可正向执行、可回滚；旧数据可读 |
| UI 壳层 / 布局 / 路由 | 主要路由 + 响应式断点 + 导航可达性 |
| 依赖升级 | 全量测试 + lint + build + 兼容性核对 |
| 配置 / CI | 构建产物或本地行为与改动前一致 |

## 硬性要求

- 回归必须覆盖**本次改动可能间接影响**的路径，而不只是直接改动的文件。
- 回归结果记录真实命令与结果。
- 发现回归 → 回到修复循环，修完重跑针对性验证，再重新回归。
- 与本次改动无关的既有失败：单独标注为 "pre-existing"，不要算在本次头上，也不要顺手修（除非用户要求）。

## 什么时候可以跳过

只有同时满足以下条件才允许"跳过回归"并在报告里写明理由：

- 改动是纯文档 / 纯注释 / 无运行时影响。
- 或改动完全局限在单一叶子模块，且无共享调用方。

UI 任务的回归至少包含：主要路由可达 + 三个宽度下无溢出与错位 + 关键交互可用。
