# Functional Testing

验证"这次改动到底有没有按请求工作"。用仓库已有的命令，不硬编码 `pytest` 或 `npm test`。

## 优先级顺序

```text
existing targeted tests   仓库里已有、直接覆盖改动路径的测试
      ↓
new targeted tests        为本次新增/修复行为补的测试
      ↓
integration tests         跨模块、跨服务、跨页面的路径
      ↓
critical manual checks    没有自动化手段时的关键手工验证
```

从上往下走，能在上一级证明的，不要在下一级重复消耗。

## 硬性要求

- **必须测试与改动直接相关的路径**。只跑一遍全量测试通过，不等于改动被验证过。
- 命令必须来自仓库真实配置：先读 `package.json` scripts、`pyproject.toml`、`Makefile`、CI 配置，确定真实的 test / lint / build / run 命令。
- 跑测试前先确认测试命令本身可用（环境、依赖、数据库、外部服务），环境缺失属于真实 blocker，按 `BLOCKED` 处理，不要伪装成通过。
- 记录真实输出：命令、通过/失败数量、关键失败信息摘要。禁止只写"测试通过"。

## 测试内容要求

- 覆盖正常路径。
- 至少覆盖一条边界或失败路径（空输入、异常、并发、权限失败、越界值）。
- bug 修复任务：把这次的 bug 复现成自动化用例，锁住它。
- 新功能任务：每个验收标准至少对应一条验证。

## 什么时候算"够"

停止条件：

- 改动相关的测试通过。
- 覆盖到验收标准的每一条。
- 没有被本次改动引入的新失败。

全量测试套件耗时很长时，可以只跑相关子集，但必须在报告里写明：跑了什么、没跑什么、为什么。

## 失败处理

```text
Failure → Analyze（根因）→ Fix（改源码）→ Re-run（针对性验证）→ Regression
```

不要第一次失败就收工，也不要为了变绿去改测试断言。修复记录写进 `07-fixes.md`，测试结果写进 `04-functional-test.md`。

## 手工验证

没有自动化手段时（UI 交互、真实数据流、部署后行为），做关键路径手工验证并记录：

- 验证了什么、在哪个环境/视口/输入下验证。
- 观察到的结果。
- 无法验证的部分（并说明原因）。

禁止把"我打算验证"写成"已验证"。
